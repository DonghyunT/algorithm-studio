## 1. 이번 전환의 의도

V3의 문항을 "버리기" 위한 작업이 아니다. 이미 만든 개념 문제와 난이도 균형을 교육 자산으로 보존하고, 학생이 단순히 용어를 기억했는지가 아니라 문제를 인식·분석·추상화·분해하고 조건을 읽어 해결 절차와 알고리즘의 작동을 판단하는지를 더 잘 확인하기 위한 전환이다.

동시에 평가용 정답과 자동 채점 근거가 학생 브라우저에 전달되는 현재 구조를 끝낸다. 학생이 GitHub 주소를 알지 않더라도 시험 페이지가 정답을 내려보내면 개발자 도구로 확인할 수 있으므로, 공개 저장소의 존재 여부와 별개로 보호 경계를 바꿔야 한다.

V3은 과거 회차 답안의 재현과 일반 연습을 위해 유지한다. V4는 새 평가 회차에서만 선택하며, V3 답안을 V4 기준으로 재채점하지 않는다.

## 2. V4 문항 품질 기준

### 학습 목표를 유지하는 방식

| 영역 | 유지할 핵심 | V4에서 높일 점검 수준 |
|---|---|---|
| 문제 인식·분석 | 해결할 문제, 필요한 결과와 조건을 찾기 | 주어진 상황에서 핵심 문제와 해결에 필요한 정보·조건을 구분 |
| 추상화·문제 분해 | 핵심 정보만 남기고, 복잡한 문제를 해결 가능한 작은 문제로 나누기 | 불필요한 정보 제거와 하위 문제 구분이 해결에 왜 필요한지 판단 |
| 해결 절차의 순서화 | 해결에 필요한 행동을 앞뒤 관계에 맞게 세우기 | 먼저·나중의 처리 순서와 빠진 단계를 구분 |
| 알고리즘의 조건 | 입력·출력·명확성·유한성·수행 가능성 | 정의를 고르는 문제뿐 아니라 실제 지시가 조건을 만족하는지 판별 |
| 순서도 기호 | 단말·자료·판단·처리 역할 | 기호 이름 암기보다 상황에 맞는 역할 선택 |
| 제어 구조 | 순차·선택·반복 | 조건의 참·거짓, 실행 순서와 반복 종료를 근거로 결과 추론 |
| 경계값과 추적 | 비교 연산과 반복 실행 | `이상/초과/미만`의 경계, 누적·남은 값·종료 시점을 한 단계씩 확인 |
| 실생활 적용 | 학생이 읽을 수 있는 생활 맥락 | 특정 가정·용어를 알아야만 풀리는 배경지식은 배제 |

### 한 문항마다 지킬 기준

1. 학생이 무엇을 판단해야 하는지 한 문장으로 설명할 수 있어야 한다.
2. 정답은 지문과 수업에서 배운 개념만으로 하나로 결정되어야 한다.
3. 오답 보기는 같은 범주와 문법 형태를 유지하되, 흔한 오개념을 반영한다. 터무니없는 보기나 글자 수 힌트는 사용하지 않는다.
4. 한 문제에 새 개념을 여러 개 겹쳐 묻지 않는다. 긴 독해력·계산 속도·가정 환경의 차이가 점수를 좌우하지 않게 한다.
5. 단답형은 허용 가능한 표기 차이를 명시적으로 검토한다. 자동 채점이 애매하면 교사 확인 대상으로 남기거나 문항을 고친다.
6. 실제 수업에서 풀이 과정 자체가 공개된 예시를 그대로 평가 문항으로 재사용하지 않는다. 같은 개념은 상황·수치·판단 경로를 새로 구성한다.

## 3. 배정과 난이도 원칙

현재 30분·총 100점 구조(Part 1 10문항 30점, Part 2 6문항 30점, Part 3 40점)는 유지한다. V4의 모든 배정 조합은 다음을 확인한다.

* Part 1에는 쉬운 개념·적용, 중간 난이도 판단, 높은 난이도 추론이 균형 있게 포함된다.
* Part 2에는 기본 기호·제어 구조 확인, 경계값 판단, 실행 추적 또는 복합 상황 판단이 균형 있게 포함된다.
* 같은 학생의 Part 1·2에 같은 정답어 또는 거의 같은 사고 과정을 중복 배정하지 않는다.
* 학생별 문항은 서로 달라도 총 난이도와 배점이 동등해야 한다. 이 값은 추측이 아니라 배정 도구의 자동 검사로 확인한다.

## 5. 초기 선택과 현재 보관 범위

현재 V4 전체 문항·정답은 공개 Git에서 분리하여 운영 환경 변수로 제공하고 교사 백업으로 내려받습니다. 교사의 수정본 관리·버전별 보관·과거 회차 복구 방식은 아직 별도 설계가 필요합니다. 웹 백업 기능을 문항 편집·게시 시스템의 구현 완료로 표시하지 않습니다.

## 6. V4 완료 조건

1. V4 실제 정답·유사 정답·비공개 채점 기준을 학생 전달 코드와 공개 저장소에 넣지 않는다. 정답을 포함하지 않는 범용 서버 채점 코드의 공개와 실제 정답 공개를 구분한다.
2. 학생은 자신에게 배정된 문항만 받고, 직접 요청을 바꾸어 다른 문항·다른 학생 기록·정답을 얻을 수 없다.
3. 서버 채점 결과가 학생이 보낸 임의 점수보다 우선하며, 제출 후 답안 변경은 기존 마감 규칙과 함께 거부된다.
4. 문항별 교육 목표·정답 근거·오개념 보기·유사 정답·난이도 점검 기록이 교사 전용 검토 자료에 남는다.
5. 기존 V3 회차 조회와 새 V4 회차의 학생·교사 대표 흐름이 각각 깨지지 않는다.

## 7. P0 구현 범위와 남은 확인

2026-09-15 `codex/secure-assessment-integrity`에서 다음을 구현하고, Firestore 기본 DB 규칙과 Vercel Production 코드를 실제 반영했다. 당시에는 V4 문항 은행 환경 변수와 V4 회차 선택을 아직 설정하지 않은 상태였다.

* `api/evaluation.js`는 익명 학생의 본인·진행 중인 V4 회차 요청에만 정답을 뺀 문항을 전달한다.
* V4 객관·단답 채점은 비공개 문항 은행과 회차·학급·번호 기반 서버 배정을 사용한다. 학생 브라우저의 점수와 임의 배정 정보는 채점에 사용하지 않는다.
* 제출된 답안은 담당 교사만 서버 채점 결과와 문항·정답·출제 의도를 볼 수 있다. 진행 중에는 교사 화면에도 정답을 표시하지 않는다.
* V4 학생 답안에는 공개 배정 정보가 저장되지 않도록 클라이언트와 Firestore 규칙을 함께 제한한다.
* 문항 은행 형식, 난이도 조합, 정답 비노출, 소유·교사 권한 경로를 자동 검사한다.

위는 2026-09-15 P0 도입 당시 범위입니다. 이후 운영 은행 등록·교사 백업·학생 점수 조회가 추가되었습니다. 현재 구현은 상단 요약과 최신 PRD를 따르고, 아래 9~10절은 남은 보관·재현·검증의 수용 기준으로 사용합니다.

현재 구조의 근거는 2026-09-15 확인한 main 기준 **7d24e50**이다. 핵심 제품 코드가 도입된 커밋은 **7c4f1ec**이다. [문항 은행 모듈](../server/evaluation-bank.cjs), [V4 API](../api/evaluation.js), [CI 설정](../.github/workflows/verify.yml)을 제한적으로 확인했다. 코드 전수 검토나 새로운 운영 보안 검증은 수행하지 않았다. 아래 완료 조건은 전부 향후 수용 기준이다.

### 9.1 회차별 문항·채점 재현 — 최우선

**현재 확인된 구조**

- V4 API는 요청 시 현재 환경 변수의 은행을 읽고, 회차·학급·번호와 배정 비밀값으로 문항을 결정적으로 다시 배정한다. 같은 입력·은행·코드·비밀값이면 같은 배정을 얻는 구조다.
- 채점은 현재 은행의 정답·허용 답·배점과 현재 채점 함수에 의존한다. 응답의 rubricVersion 문자열만으로 과거 은행·채점 코드가 보존되는 것은 아니다.
- API는 현재 classrooms 세션과 students 경로를 읽는다. 기존 archives 자료가 존재하는 것만으로 V4 과거 회차 배정·채점 조회까지 구현되었다고 볼 수 없다.

**발생 가능한 문제**

- 9월 평가 후 은행에 문항을 추가하거나 순서를 바꾸면 10월에 같은 배정 요청을 해도 9월과 다른 문제가 뽑힐 수 있다.
- 문항 ID를 유지해도 보기 순서·정답·허용 답·배점 또는 답안 정규화 규칙을 바꾸면 기존 답안의 의미나 점수가 바뀔 수 있다.
- 최신 기준으로 다시 계산한 값을 확정 성적으로 취급하면 교사 확인 없이 이전 성적이 바뀔 수 있다.

**권장 방향**

- 평가 당시 문제 본문·보기 순서·학생별 배정·정답/허용 답·배점·채점 기준을 고정하고 수정본은 새 회차부터 적용한다.
- 자동 계산 참고값과 교사 확정 성적을 구분한다. 문항 업데이트·조회·새 배포만으로 확정 성적이 변경되지 않아야 한다.
- 현재와 보관 회차에서 당시 답안·문항·확정 성적을 확인할 수 있게 하고, 복구에 필요한 의존 자료를 함께 보존한다.

**결정 필요 사항**

| 비교할 방식 | 확인할 이점과 부담 |
|---|---|
| 변경 불가 은행 버전 + 학생별 문항 ID/순서 참조 | 중복 보관 감소, 참조 대상과 보기·채점 버전의 영구 일치 필요 |
| 회차/배정별 원본 사본 보관 | 당시 내용 확인 용이, 저장량·접근 제어·사본 관리 부담 |
| 버전별 은행과 배정 재생성에 필요한 비밀값·알고리즘 보존 | 재생성 가능성, 은행 순서·알고리즘·키 버전까지 함께 고정할 필요 |

문항 ID만 저장하거나 버전 번호만 붙이는 것으로 충분하다고 결론내리지 않는다. 조합 가능성을 포함해 저장·조회·복구 흐름을 비교한다. 보관 기간, 비밀값 교체 및 유출 시 대응, 성적 정정 권한·절차·이력은 별도 결정한다. 실제 필드명·컬렉션·API는 아직 정하지 않는다.

**완료 조건**

새 은행·비밀값·배정/채점 코드 버전을 도입한 뒤에도 기존 회차를 당시 기준으로 재현하고 현재·보관 회차에서 확인할 수 있어야 한다. 확정 성적은 그대로 남고, 의도적인 정정은 합의한 절차로만 이루어져야 한다.

### 9.2 비공개 문항 보관과 다른 PC 접근

**현재 확인된 구조**

P0는 실제 정답을 공개 저장소에서 분리하기 위해 은행 전체 JSON을 EVAL_BANK_V4_JSON으로 읽는다. 2026-09-15 제한적 확인 당시에는 실제 은행이 아직 등록 전으로 기록되었으나, 2026-09-18 현재 선생님 확인에 따라 V4 운영 은행·환경 변수가 등록되어 운영 중이다. 이 길이는 JavaScript 문자열 길이이며 배포 플랫폼의 바이트 용량 제한과 같지 않다.

**발생 가능한 문제**

- 환경 변수에 큰 JSON을 직접 붙여넣으면 교사의 문항 검토·수정 이력 비교·오류 복구가 불편하다. 은행을 덮어쓰면 이전 회차의 근거를 잃을 수 있다.
- Vercel은 Node.js 등 런타임에서 배포별 환경 변수 이름·값 전체에 64KB 제한을 두며 단일 변수도 이 한도를 넘을 수 없다. 코드 길이 검사 통과가 등록 가능성을 보장하지 않는다. 한글 등을 포함한 실제 바이트 크기와 다른 변수의 사용량도 고려해야 한다. [공식 제한](https://vercel.com/docs/limits#environment-variables), 2026-09-15 확인.
- Git 제외 파일은 PC 간 자동 전달되지 않으며, 개인 PC 하나에만 있는 원본을 운영 자료의 유일한 보관본으로 가정할 수 없다.

**권장 방향**

비밀키·연결 설정과 문항 콘텐츠의 관리를 분리하는 방향으로 검토한다. 선생님이 보호된 경로에서 검토·수정하고 이전 버전을 찾을 수 있어야 한다. 처음부터 큰 문항 관리 시스템을 만들거나 특정 서비스로 이전하는 것은 이번 합의가 아니다.

**결정 필요 사항**

저장 후보마다 아래 질문에 답하는 비교표를 만든 뒤 선택한다.

| 기준 | 구현 전 확인할 질문 |
|---|---|
| 교사 접근성 | 별도 개발 도구 없이 검토할 수 있는가? 편집·게시를 누가 하는가? |
| 수정 이력·회차 재현 | 이전 버전을 고정·조회할 수 있는가? 진행 중 회차가 영향받는가? |
| 비공개 범위 | 서버·담당 교사·문항 관리자에게 각각 무엇을 허용할 것인가? |
| 백업·복구 | 삭제·오입력·계정 접근 불가 때 어떻게 복원하고 누가 확인하는가? |
| 다른 PC 접근 | 어떤 계정으로 원본·이력을 받으며 로컬 비밀 파일 없이 이어갈 수 있는가? |
| 비용·운영 부담 | 저장·조회·백업 비용과 교사의 관리 단계는 얼마나 늘어나는가? |

현재 전달 경로는 운영 환경 변수와 교사 백업이다. 버전별 보관 서비스·관리 계정·보관 기간과 복구 절차는 미정이다. 공개 문서에는 실제 V4 문항·정답·학생 자료·비밀값을 넣지 않는다. 학생이 받는 본인 문항과 교사용 전체 은행을 구분한다.

**완료 조건**

다른 PC에서 승인된 계정으로 동일 버전의 교사용 자료를 확인하고, 새 버전 준비와 이전 버전 복구를 재현할 수 있어야 한다. 공개 소스·학생 배포물·무권한 응답에 비공개 자료가 없어야 하며 저장/배포 용량 검사를 통과해야 한다.

### 9.3 보안·저장 검증

**현재 확인된 구조**

V4 API에는 인증·본인 소유·담당 교사·회차·제출 상태 검사가 있고 학생 응답에서 정답·출제 의도를 제외한다. CI는 문법·로컬 참조 및 단위/API 검사를 실행한다. V4 규칙 배포 기록과 운영 API GET의 405 응답은 존재하지만 실제 V4 평가 전체의 성공 증거는 아니다. 현재 V3의 학생 코드 내 정답 노출 한계는 그대로 구분한다.

**발생 가능한 문제**

API의 모의 응답 검사만으로 Firestore에 직접 요청한 경우의 거부를 보장할 수 없다. 반대로 규칙 검사가 통과해도 서버 응답에 정답이 섞이는지까지 확인한 것은 아니다. Preview의 운영 Firebase 연결, 저장 실패 후 잘못된 완료 표시, 마감·회차 전환 중 늦은 요청도 확인이 필요하다.

**권장 방향**

학생은 본인에게 필요한 문항만 받고 정답·출제 의도는 권한 있는 교사 경로에서만 확인한다. API 요청과 Firestore 직접 요청을 각각 시험하며 실패 상황에서 작성 답안을 보호한다. 검증 자료는 실제 학생 자료와 분리한다.

| 검사 종류 | 확인 범위 | 대신할 수 없는 검사 |
|---|---|---|
| 문법·로컬 참조 | 파싱 오류·누락 파일 | 권한·저장 동작 |
| 단위·모의 API | 배정·채점·응답·분기 로직 | 실제 Firestore 규칙·운영 인증 |
| 에뮬레이터 규칙 | 역할·문서 상태별 직접 접근 허용/거부 | 실제 프로젝트 설정·배포·교실 네트워크 |
| 분리된 실제 환경 | 로그인·저장·제출·교사 조회·환경 설정 | 모든 교실 기기·전체 동시 사용 |
| 소규모/교실 검증 | 실제 기기·실패 복구·동시 사용 | 임의의 모든 상황에 대한 무오류 보장 |

Firebase 공식 도구는 에뮬레이터에서 인증 상황을 모의하여 규칙의 허용/거부를 검사할 수 있게 한다. 이는 권장 검증 수단이며 이번에 설치·구현·실행한 것이 아니다. [공식 규칙 검사 안내](https://firebase.google.com/docs/firestore/security/test-rules-emulator), 2026-09-15 확인.

**결정 필요 사항**

테스트 전용 프로젝트 또는 승인된 검증 환경, 테스트 계정·자료, 운영 자료와의 분리·정리 방법, 교실 대표 기기와 동시 인원을 정한다. 보관·마감·성적 정정 정책이 필요한 시나리오는 먼저 해당 정책을 확정한다.

**완료 조건**

아래 10절에서 API와 직접 DB 요청의 결과를 각각 기록한다. 실패·미검증을 숨기지 않고 운영 전환을 막는 항목은 해결하거나 선생님과 범위를 다시 합의한다. 설정 누락을 임의의 V3 문제·빈 문제·자동 합격으로 대체하지 않는다.

### 9.4 유지보수와 단계적 전환

**현재 확인된 구조**

프런트엔드는 Vanilla JS이며 순서도·평가·교사 화면 파일에 여러 역할이 함께 있다. V4 서버 은행·API는 분리되어 있지만 회차 보관·교사 조회와 연결해 확인할 부분이 남아 있다. 파일 크기만으로 결함이라고 판단하지 않는다.

**발생 가능한 문제**

한 파일에서 화면·실행·통신·채점이 함께 바뀌면 수정 영향과 회귀 원인을 좁히기 어렵다. 전체 재작성이나 V3 일괄 전환을 문항 개선에 묶으면 기존 수업·성적의 위험이 커진다.

**권장 방향**

관련 기능을 수정할 때 화면 표시, 순서도 실행, 서버 통신, 배정·채점의 역할을 작은 단위로 분리한다. 기존 동작과 인터페이스를 확인하면서 진행하고 전면 재작성·프레임워크 전환은 포함하지 않는다. 문항 품질 작업은 계속하되 회차 재현·비공개 보관·권한 검증을 실제 활성화의 선행 조건으로 둔다.

**결정 필요 사항**

각 작업의 영향 범위·분리 경계·호환 검사와 운영 중단 시 복구 절차를 구현 전에 정한다. V4 문제가 생겼다고 진행 중인 회차를 V3으로 바꾸거나 옛 공개 규칙으로 되돌리지 않는다. 복구 가능한 배포 코드·은행·배정·채점 버전의 조합과 학생의 미전송 답안 처리도 함께 검토한다.

**완료 조건**

변경 관련 학생·교사 흐름과 V3 기존 회차가 유지되고, 새로운 V4 회차의 정상·실패 경로가 검증되어야 한다. 공통 엔진·인증·저장·채점 변경은 프로젝트 규칙에 따른 전체 회귀검사를 수행한다. 문서 작업만 한 이번에는 제품 검사를 반복하지 않는다.

## 10. 다음 구현에서 사용할 검증표

**모두 향후 수용 기준이며 이번 문서화로 통과한 항목은 없다.** 사례는 실제 문항·학생 자료 대신 검증용 자료로 구성한다. 각 실행 기록에는 날짜, Git 커밋, 은행/채점 버전, 환경, 역할, 기대 결과, 실제 결과, 근거 위치와 남은 제한을 남긴다. 운영 기록을 새 버전의 재검증 결과로 재사용하지 않는다.

| 영역 | 대표 사례 | 기대 결과·완료 근거 |
|---|---|---|
| 과거 회차 | 은행 추가·재정렬, 보기/허용 답/배점·키·채점 코드 변경 | 기존 문제·배정·채점 기준과 확정 성적 유지 |
| 교사 성적 확인 | 현재 회차를 보관한 뒤 다시 조회 | 당시 답안·문제·확정 성적 확인, 최신 은행으로 조용히 대체하지 않음 |
| 학생 권한 | 다른 번호·계정·회차 요청 및 직접 DB 접근 | 타 학생 자료·문항·정답 접근 거부 |
| 교사 권한 | 미로그인·학생·타 반 교사·권한 회수 계정 | 담당 범위 밖 답안·정답 조회 거부 |

## 12. V3 모의 → V4 실제 평가와 AI 채점 토의 기록

2026-09-15 KST. **확정한 운영 방향, 코드에서 확인한 사실, 제안, 답변 대기를 구분**한다. 아래 계획 기록은 당시 시점의 내용이다. 2026-09-18 현재 선생님 확인에 따라 V4도 운영에 적용되어 있으며, 다음 에이전트는 8~11절의 운영 보완 조건으로 이어간다.

### 12.1 선생님이 변경한 방향

| 구분 | 합의와 현재 상태 |
|---|---|
| 이번 주 | 2026-09-14~09-20 주간에 V3 모의 수행평가 진행 |
| 다음 주 | 2026-09-21~09-27 주간에 V4 실제 수행평가를 진행하는 목표 |
| 날짜·대상 | 실제 수업 날짜·반·인원·사전 점검 가능 시간은 답변 대기 |
| 이전 가정 | V3와 V4를 같은 실제 평가에 반별로 혼용한다는 가정은 철회 |
| AI 채점 | 개선 의사 있음. 어떤 문제가 불편한지·원하는 판단 기준·모델 변경 여부는 차후 답변 |

V4 활성화는 목표 날짜만으로 결정하지 않는다. 미충족 조건이 있으면 남은 작업과 대안을 제시하고 판단을 받는다. 모의 기록의 삭제·재채점·공식 성적 반영을 임의로 실행하지 않는다. 실제 평가에서 모의와 같은 문제를 그대로 재사용할지, 배운 범위를 어떻게 반영할지는 문항 검토 때 확인한다.

### 12.2 V3 모의 수행평가에서 관찰할 것

2026-09-15 당시 기본 회차는 V3로 기록되어 있었고 과거 문항 배정·저장·제출 오류의 수정 배포 기록이 있다. 2026-09-18 현재는 V4도 운영 중이며 V3는 모의평가·기존 회차 호환용으로 유지한다. 문서 변경이나 운영 적용 사실을 현재 교실에서 전 과정이 다시 통과했다는 의미로 표현하지 않는다. V3에는 학생 코드에 정답이 포함되는 기존 한계가 남아 있다.

| 항목 | 선생님이 관찰·판단할 부분 | 에이전트가 확인할 부분 |
|---|---|---|
| 준비·입장 | 반·시간·입력 안내, 번호·이름 실수 시 학생이 경로를 이해하는지 | V3 회차, 두 학생 입장·번호 중복·문항 배정 |
| 문제 표시 | 애매한 지문·보기, 읽기 부담, 화면 크기·입력 불편 | 괄호·줄바꿈·화면 잘림·키보드 가림·터치 |
| 작성·복구 | 막히는 단계, 새로고침/연결 장애 시 필요한 안내 | 같은 탭 새로고침, 답안 유지, 탭 이탈 후 저장 |
| 제출 | 미완성 제출 안내, 종료 때 혼란, 소요 시간 | 수동 제출·시간 만료·교사 종료·실패 후 재시도 |
| 교사 확인 | 제출 인원, 답안·순서도 이해, 확인 작업 부담 | 제출 기록·순서도 조회·점수 확정·CSV 반영 |
| 장애 대응 | 학생 지원 방식·재시험 필요 여부 | 미전송 답안 보호, 재접속·재시험이 기존 기록에 주는 영향 |

고의적인 실패·권한 검사는 시험용 환경·자료로 한다. 실제 모의 수업의 학생 답안을 시험 편의상 초기화하지 않는다. 관찰 결과는 시간·기기·동작·화면 안내·복구 결과 위주로 기록하고, 공개 Git에 이름·답안 원문 등 개인정보를 올리지 않는다. 학생에게 별도 성찰 보고서나 추가 채점 과제를 요구하지 않는다.

### 12.3 V4 실제 수행평가 준비 판단

선생님은 수업에서 배운 범위, 지문의 명확성, 예상 풀이 시간, 도움 범위, 평가 기준을 판단한다. 에이전트는 다음을 검증 가능한 형태로 준비한다.

1. 문항별 목표·정답·허용 답·배점과 모의 문제의 단순 재사용/단서 노출 여부를 검토한다.
2. 비공개 보관·다른 PC 접근과 당시 문항/배정/채점/확정 성적의 보존·복구를 마련한다.
3. 학생에게 본인 문항만 전달하고 API·직접 DB의 타인 접근을 거부하는지 확인한다.
4. 작성 → 저장 → 제출 → 교사 답안 확인 → 점수 확정까지 연결한다.
5. V4에서 Part 3 AI 초벌 검토와 교사 직접 채점·확정 경로가 함께 동작하는지 확인한다. AI 없이도 교사가 직접 평가할 경로를 유지한다.
6. 설정 누락·권한 오류·통신 실패·회차 전환에서 임의 문제나 완료 상태로 대체하지 않는지 확인한다.

기존 난이도 가중치 합이 같은 것은 설계상 균형이지 실제 학생의 체감 난이도 동등성을 입증하지 않는다. 모의 관찰을 실제 문항의 읽기 부담·풀이 시간 검토에 활용하되, 가중치만으로 품질 검토를 끝내지 않는다. 전체 기술 수용 기준은 10절을 따른다.

### 12.4 AI 초벌 채점: 먼저 기준, 다음 비교, 마지막 적용

**현재 코드에서 확인한 사실 — b410a63 기준, 2026-09-15 제한적 확인**

> 이 subsection의 코드 사실은 2026-09-15 기준 기록입니다. 이후 V4 운영 적용 및 V3/V4 AI 채점 범위 변경은 최신 PRD·코드·배포 기록으로 별도 확인해야 하며, 아래 기록만으로 현재 운영 상태를 판단하지 않습니다.

- [AI 평가 API](../api/assessment.js)는 교사 초벌 검토에 questionVersion === 3을 요구한다. V4 Part 1·2 서버 기능이 있어도 Part 3 AI 연결이 자동으로 끝난 상태는 아니다.

- 결과에는 모델명·회차·답안 기준·open-design-v1을 기록하지만 지시문 개정 버전은 별도로 구분하지 않는다. 모델명만으로 당시 지시문까지 재현된다고 보지 않는다.
- AI는 네 항목별 0~10점의 제안·근거·불확실성을 반환하고 교사가 별도 확정한다. 장애는 0점이 아닌 직접 검토 안내다.
- 현재 지시문에는 만점 남발을 피하고 엄격하게 평가하라는 표현이 있다. 실제로 점수가 지나치게 낮거나 높다는 결론은 대표 답안 비교 전에는 내리지 않는다.

**선생님께 확인할 판단 경계 — 아직 점수 규칙을 정한 것이 아님**

**제안이며 승인·실행 전인 비교 방법**

대표 답안 8~12개 정도를 에이전트가 준비하고, 선생님은 기대 점수·이유를 간단히 확인하는 방법을 제안했다. 정해진 필수 표본 수나 점수 허용 오차가 아니며 실제 학생 자료 사용·AI 호출 승인은 별도로 확인한다. 공개 문서에는 비공개 문항·학생 원문을 넣지 않는다.

같은 답안을 현재 방식과 개선안으로 비교하여 항목별 차이, 반복 요청의 점수 흔들림, 없는 근거 생성, 정상 반복·단순 해결책의 오판, 답안 속 점수 요구에 대한 반응, 교사 확인 사항, 지연·실패·비용을 살핀다. 점수를 무조건 높이거나 낮추기보다 기준과 증거를 명확히 하는 방향을 권장했다. 구체적인 모델·지시문·통과 기준은 미정이다.

문제 버전(V3/V4), AI 모델, 채점 기준·지시문 버전은 구분해 검토한다. 새 모델이나 지시문으로 재요청해도 기존 교사 확정 성적이 덮어써지지 않아야 한다. 채점 설정 분리가 필요한지 검토하고 실습 AI·학생 조건 추천에 미치는 영향을 함께 확인한다.
