## 간단한 개발 흐름

1. 요구사항과 재현 사례를 문서로 확인한다.
2. 개발 브랜치에서 목적별로 수정하고 작은 커밋으로 기록한다.
3. 기존 오류를 재현하는 검사와 정상 사용 흐름을 함께 검증한다.
4. 변경 내용·검증 결과·남은 제한을 정리하고 검토 요청(PR)을 준비한다.
5. main 병합·배포에 대한 선생님의 명시적 승인을 확인하고 진행한다. 이번 작업처럼 검증 후 병합·배포까지 이미 승인한 경우 동일 승인을 다시 요청하지 않는다.

main에 push하면 운영 Vercel 배포가 실행될 수 있으므로 승인 전 main 병합·push를 하지 않는다. 미리보기 배포도 운영 Firebase와 자동 분리되는 것은 아니다. 테스트에서 운영 DB를 쓰지 않도록 구성한 뒤 미리보기를 사용한다. Firestore 규칙 배포는 Git 브랜치와 별개로 운영에 영향을 주므로 별도 검증 후 적용한다.

## V4 개발을 시작할 때

[V4 계획 8~11절](EVALUATION_V4_PLAN.md#8-다음-순서와-활성화-조건)에 회차 재현·비공개 보관·보안 검증·유지보수의 현재 사실과 권장 방향, 미결정 사항, 향후 수용 기준을 통합했다. 기존 P0를 재구축하지 말고 보관과 회차 재현 설계부터 확인한다. 문서화 승인은 구현·저장 서비스 선정·데이터 변경 승인이 아니다.

관련 기능을 수정할 때 화면·실행·통신·채점의 역할을 점진적으로 분리한다. Vanilla JS를 유지하고 문항 개선에 전체 재작성이나 프레임워크 전환을 묶지 않는다. API 모의 검사와 Firestore 직접 접근 규칙 검사는 각각 필요하며 에뮬레이터 통과를 운영 검증으로 표현하지 않는다. 공통 엔진·인증·저장·채점 변경의 전체 회귀검사는 AGENTS를 따른다.

문서만 수정하면 링크·용어·상태·근거와 차이를 검토한다. 앱 전체 회귀검사·운영 DB 검사는 반복하지 않는다. 구현 검증에는 날짜·Git 버전·은행/채점 버전·환경·사례·실제 결과·근거를 남기고 미검증은 그대로 표시한다.

## 완료 보고에 포함할 내용

* 무엇이 달라졌는지와 학생·교사에게 미치는 영향
* 실행한 검사, 통과·실패, 환경과 버전
* 해결한 감사 항목과 남은 항목
* 인증 설정·운영 배포 등 후속 작업

자동 검증 통과만으로 모든 교실 환경의 정상 동작을 보장하지 않는다. 미검증 항목은 명확히 남긴다.

초기 검토 버전의 실행법과 결과는 [구현 검토서](IMPLEMENTATION_REVIEW.md), 운영 전환 조건은 [운영 준비](OPERATIONS.md)를 참고한다. 초기 로컬 검토 이후 원격 push와 운영 배포가 완료되었으며 최신 상태는 배포 기록을 따른다. 미리보기에서 실제 DB를 쓰는지 확인한 뒤 검증한다.
