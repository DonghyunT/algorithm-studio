# 운영 설정과 추가 검증

> 갱신: 2026-09-21. 기존 인증·담당 반 권한·V4 운영 설정은 반영되어 있습니다. 새 PC에서 초기 구축을 반복하지 않습니다. 현재 상태는 [인수인계](HANDOFF.md), 반영 근거는 [배포 기록](DEPLOYMENT.md), 문항 백업과 변경 절차는 [V4 설정](EVALUATION_V4_SETUP.md)을 따릅니다.

## 일상 운영과 장애 대응

교사는 평가 준비 전에 실전평가(V4, 기본값) 또는 모의평가(V3)를 선택합니다. V4만 AI 초벌 채점을 사용하며 교사 확정과 구분합니다. 새 평가 준비는 이전 회차 보관을 수반하므로 재접속 문제를 해결하려고 선택하지 않습니다.

- PC 재시작 후 같은 번호로 돌아오지 못하면 교사 상세 화면의 답안 유지 재접속 허용을 사용합니다. 서버에 저장된 답안을 이어가는 경로이며 아직 전송되지 않은 로컬 변경까지 복원하는 것은 아닙니다.
- 처음부터 다시 풀기는 답안 유지 재접속과 다릅니다. 결시생 개별 추가 응시는 시험 종료 후 결시생에게 개별 30분 타이머를 부여하고 어느 기기에서든 접속할 수 있게 지원하며, 0점 자동 마감된 결시생이라도 교사가 안전하게 초기화(`forceReset: true`)하여 응시 기회를 다시 부여할 수 있습니다. 기존 답안을 이어가려는 학생에게 대신 사용하지 않습니다.
- 종료·제출은 실제 저장 결과를 확인합니다. V4 은행 백업은 문항 백업이며 학생 기록·배정 비밀값까지 복원하는 백업이 아닙니다.

위 동작의 현재 코드와 명세를 확인했으며 이번 문서 작업에서 운영 수업을 재현하지 않았습니다. API·직접 DB 권한, 재접속·추가 응시의 실제 환경 검증은 별도로 기록해야 합니다.

## 기존 운영과 초기 구축 기록

이 문서는 사용자 승인에 따른 운영 반영 절차입니다. 초기 이전 형식의 테스트 자료는 `eval_sessions`에 보존합니다. 현재 `classrooms`의 학생 자료를 테스트 자료로 간주하거나 초기화하지 않습니다. 새 앱은 [classrooms 구조](DATABASE.md)를 사용합니다. Google·익명 인증, 승인 도메인, 새 학급 11개와 Firestore 규칙을 설정했고 실제 학생 권한 검사 13개를 통과했습니다. 교사 Google 로그인 확인과 이후 운영 화면 검사 기록은 배포 기록을 따르며 학급 동시 사용 검증은 별도입니다.

## 먼저 분리된 검토 환경

로컬에서는 `node tools/preview.cjs`로 시연합니다. Vercel Preview는 기본적으로 운영 Firebase 설정을 그대로 읽으므로 브랜치 push만으로 안전한 테스트 환경이 되지 않습니다. 원격 PR/Preview를 만들기 전 테스트 전용 Firebase 프로젝트 설정 또는 Preview에서 원격 저장을 차단하는 구성이 필요합니다. 로컬 시연은 로그인·서버 권한 시험을 대신하지 않습니다.

## 신규 검증 환경의 Firebase 인증과 데이터

1. 테스트 프로젝트의 Authentication → Sign-in method에서 Google과 Anonymous 제공자를 활성화합니다. Google 공급자의 지원 이메일을 설정합니다.
2. Authentication의 승인 도메인에 사용할 테스트 도메인을 등록합니다. 운영 적용 시 실제 Vercel 도메인도 확인합니다.
3. 교사 Google 계정으로 로그인한 뒤 Authentication의 Users에서 해당 UID를 확인합니다. 관리자가 Firestore `teachers/{해당 UID}` 문서를 만들고 `enabled: true`와 담당 범위(`allClasses: true` 또는 승인된 `classIds`)를 함께 지정합니다. enabled만 있는 역할은 접근할 수 없습니다. 기존 운영 역할을 새 PC에서 재등록하지 않습니다. 이메일 이름이나 학생 입력값으로 권한을 주지 않습니다.
4. 기존 테스트 `eval_sessions`/`students` 기록은 `ownerUid`, 세션 `deadlineMs`가 없는 이전 형식입니다. 그대로 운영 데이터로 사용하지 않습니다. 백업 여부와 시험용 초기화를 확인한 뒤 새 테스트 좌석으로 검증합니다. 이 브랜치가 기존 자료를 자동 삭제하거나 마이그레이션하지는 않습니다.
5. 테스트 환경에 새 규칙을 적용하고 교사, 학생 A, 학생 B, 미로그인 사용자의 네 역할로 시험합니다. 학생 B가 A의 문서를 읽거나 변경하지 못하고, 학생이 세션·점수·교사 역할을 변경하지 못해야 합니다.
6. 마감 전 자동 저장, 마감 후 수정 거부, 같은 답안 제출 확정, 제출 직후 네트워크 단절 및 재시도, 교사 초기화, 다른 PC에서의 복귀를 확인합니다.

답안 초기화와 답안 유지 재접속은 구분합니다. 개별 재시험 초기화는 기존 답안을 보관하며, 재접속 허용은 새 UID로 기존 서버 답안을 이어가는 경로입니다. 시간이 끝나면 새 평가 준비로 전체 회차를 보관한 뒤 새 대기실을 엽니다. 이때 번호 문서가 새로 생성되므로 새 인증 UID로 입장할 수 있습니다. 다음 학생이 같은 창을 쓰기 전 '로그아웃 · 사용 종료'를 사용하거나 창을 닫습니다. 미제출 상태의 사용 종료는 차단합니다.

## AI와 Vercel

서버 환경변수 `UPSTAGE_API_KEY`를 설정합니다. `FIREBASE_PROJECT_ID`는 Firebase Web 설정의 프로젝트와 일치해야 합니다. `SOLAR_MODEL`은 필요 시 서버에서 지정합니다. API 키를 소스, 브라우저 설정, 문서에 넣지 않습니다. 기존 로컬 `config.js`는 더 이상 로드하지 않으며 배포 제외 목록에 있습니다.

API는 Firebase ID 토큰 서명/발급자/프로젝트/만료를 검증하고 고정된 응답 길이를 사용합니다. UID별 분당 10회는 인스턴스별 제한이며 추가로 Firestore 공통 일일 카운터로 전체 1,000회를 제한합니다. 현재 서버는 전달된 한도 값을 1,000회로 고정하므로 `AI_DAILY_LIMIT` 변경만으로 한도를 조정할 수 있다고 안내하지 않습니다. 오류 시 사용량 확인을 건너뛰지 않습니다. 평가 중 AI 차단은 앱 상태에 따른 클라이언트 제한으로, 다른 창·직접 API 요청까지 통제하지 않습니다. 학급 구성원 확인은 별도 보완 대상입니다.

실제 모델 응답, 로그인 토큰 갱신, 시간 초과, 사용량/비용 제한을 테스트 키와 테스트 프로젝트에서 확인합니다. `.vercelignore`가 문서·테스트·비밀 파일을 제외하는지 배포 산출물도 확인합니다.

## 승인 후 운영 반영

테스트 결과와 남은 제한을 교사가 검토한 뒤 main 병합을 명시적으로 승인합니다. Firestore 규칙은 Git 병합과 별개로 적용됩니다. 앱·규칙 변경 시 이전 버전과의 호환성을 확인하고 수업 중 전환을 피하며, 앱/규칙/인증 설정을 함께 반영할 시간을 정합니다. 이전의 공개 규칙으로 되돌리는 방식의 롤백은 사용하지 않습니다.

운영에서 교사 로그인, 시험용 학생 제출, 교사 조회, CSV를 확인한 뒤 학급 사용을 시작합니다. 실제 27명 동시 접속과 NEIS CSV 가져오기는 별도 확인 항목입니다. 서버 보관·삭제 기간도 수업 운영 전에 정해야 합니다.
